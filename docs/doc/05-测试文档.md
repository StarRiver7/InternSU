## 1 文档概述

### 1.1 编写目的

本文档基于 InternSU 项目已实现的源码，从测试角度全面分析系统的测试范围、测试策略、测试用例和潜在风险。作为项目质量保障的核心文档，本文档可用于：

- **开发人员**: 理解测试覆盖范围，定位潜在问题
- **测试人员**: 作为测试用例设计和执行的依据
- **项目评审人员**: 评估系统质量和工程规范性
- **面试官**: 快速理解测试设计思维和工程能力

### 1.2 测试目标

| 目标 | 说明 | 代码依据 |
|------|------|---------|

## 4 测试策略

### 4.1 功能测试

**目的**: 验证每个功能模块的输入输出是否符合预期。

**范围**: 用户注册/登录、会话创建/删除、消息发送、文档上传、知识空间管理。

**方法**: 黑盒测试，基于需求规格设计用例。

### 4.2 接口测试

**目的**: 验证 REST API 的请求参数、响应格式、状态码。

**范围**: 24 个 Java API + 13 个 Python API。

**方法**: 使用 Postman/curl 构造请求，验证响应。

### 4.3 集成测试

**目的**: 验证 Java ↔ Python 服务协作。

**范围**: SSE 流式代理、SQL 执行内部调用、会话持久化。

**方法**: 端到端测试，模拟完整用户操作流程。

### 4.4 权限测试

**目的**: 验证 JWT 认证、RBAC 授权、数据隔离。

**范围**: 未登录访问、Token 过期、越权访问、跨用户访问。

**方法**: 构造伪造/过期 Token，验证权限拦截。

### 4.5 异常测试

**目的**: 验证系统在异常条件下的容错能力。

**范围**: 数据库断开、Redis 不可用、LLM 调用失败、Tool 超时、非法参数。

**方法**: 模拟故障场景，验证降级和错误处理。

### 4.6 AI 能力测试

**目的**: 验证 Agent、Tool、Workflow、RAG、Trace 的正确性。

**范围**: 意图识别准确率、工具选择正确性、RAG 检索相关性、Trace 完整性。

**方法**: 构造标准问题集，评估 AI 输出质量。

### 4.7 性能测试

**目的**: 验证系统在高并发和大数据量下的表现。

**范围**: 响应时间、并发能力、SSE 流式输出。

**方法**: JMeter/Locust 压力测试。

### 4.8 安全测试

**目的**: 验证系统安全防护能力。

**范围**: JWT 伪造、SQL 注入、XSS、CSRF、Token 黑名单。

**方法**: 安全扫描工具 + 手动测试。

## 18 面试官关注点

### Q1: 为什么设计异常测试?

**基于代码的分析**: 系统依赖外部服务 (LLM API, MySQL, Redis, Milvus)，任一服务不可用都会影响核心功能。`chat_api.py` 的 try/except + 降级方案、`ToolManager` 的超时控制、`rag_pipeline.py` 的检索降级，都需要通过异常测试验证。

### Q2: 为什么设计 RAG 测试?

**基于代码的分析**: RAG 是系统核心能力之一，涉及 5 个阶段 (解析→分块→向量化→检索→生成)，任何阶段出错都会影响回答质量。需要验证分块大小 (512 字符)、向量维度 (1024)、检索准确率、引用标注正确性。

### Q3: 为什么设计 Tool 失败测试?

**基于代码的分析**: `ToolManager.execute()` 包含超时控制、参数校验、异常捕获。Tool 执行失败时需要返回 `ToolResult(success=False)`，Agent 需要优雅降级而非崩溃。测试需验证: 超时取消、异常捕获、错误传播。

### Q4: 为什么设计权限测试?

**基于代码的分析**: 系统采用 JWT 双 Token + RBAC 四级角色。`JwtAuthenticationFilter` 负责 Token 校验，`@PreAuthorize` 注解控制接口访问，`visibility` + `department_id` 控制数据隔离。测试需验证: Token 伪造、过期、越权、跨用户访问。

### Q5: 如何验证 AI 输出质量?

**基于代码的分析**: AI 输出质量依赖三个因素:
1. **意图识别**: `intent_node.py` 的 TOOLS_PROMPT 设计
2. **检索质量**: `rag_pipeline.py` 的混合检索 + 重排序
3. **生成质量**: `chat_node.py` 的 System Prompt 设计

测试方法: 构造标准问题集 (50+ 题)，评估意图识别准确率、检索召回率、回答准确率。

### Q6: 如何测试 SSE 流式输出?

**基于代码的分析**: SSE 流涉及 Python (asyncio.Queue + StreamingResponse) → Java (WebClient 代理) → 前端 (EventSource)。测试需验证:
1. 流式输出延迟 (< 2s 首 Token)
2. 客户端断开时后台 Task 自动取消
3. SSE 事件格式正确 (trace/token/meta/done)
4. 流中断后重连恢复

### Q7: 测试覆盖率如何保证?

**基于代码的分析**: 当前项目有以下测试:
- `python-ai-service/` 下有 pytest 测试文件 (form-api.test.ts, drawer-api.test.ts 等)
- Java 侧有 Spring Security Test + Mockito
- 前端无自动化测试

建议: 补充单元测试 (核心节点) + 集成测试 (端到端) + E2E 测试 (Playwright)。

### Q8: 如何设计性能测试?

**基于代码的分析**: 关键性能指标:
1. **首 Token 延迟**: SSE 流式架构，目标 < 2s
2. **会话切换**: Redis 缓存，目标 < 100ms
3. **向量检索**: Milvus IVF_FLAT，目标 < 500ms
4. **并发能力**: 50 用户同时聊天

测试工具: JMeter (REST API) + Locust (SSE 流) + 自定义脚本 (AI 输出质量)。
